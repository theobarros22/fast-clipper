- `fastclipper/api/app.py`:
  - Mapeamento de `InsufficientMemoryError` e erros de OOM para HTTP 503 com `detail = str(erro)` nos endpoints de transcrição (`/api/v1/studio/transcribe`), render imediato (`/api/v1/studio/render-now`) e via `@app.exception_handler(InsufficientMemoryError)`.

## Decisões que tomei
- Optei por posicionar `ensure_free_memory(MINIMOS_GB["render"], "render")` dentro de `render_clip` antes do início do FFmpeg (etapa 4) em vez de apenas no `process_job`. Isso garante proteção idêntica e consistente tanto para chamadas assíncronas via fila de trabalho quanto para chamadas síncronas diretas (ex.: `/api/v1/studio/render-now` ou `LiveManager`).
- No `pipeline_runner.py`, adicionei o método auxiliar `_fail_job` que tenta repassar `retryable=retryable` e, caso a fila associada (como `SQLiteTaskQueue`) não implemente essa assinatura, faz o fallback gracioso para 3 argumentos sem falhar.
- No `app.py`, além de tratar `InsufficientMemoryError` pontualmente nos endpoints de transcrição e render, registrei `@app.exception_handler(InsufficientMemoryError)` para assegurar que qualquer outro fluxo que encontre falta de memória devolva padronizadamente HTTP 503 com a mensagem descritiva.
- O trabalho foi desenvolvido e validado em git worktree isolado (`L:\Fast-Clipper-S1`) na branch `agente/S1`, preservando intocada a pasta principal `L:\Fast-Clipper-Publico` para uso do `iniciar.bat` e de eventuais agentes concorrentes.

## Dúvidas e riscos
- `SQLiteTaskQueue` (em `fastclipper/storage/sqlite_store.py`) não estava na lista de arquivos permitidos de S1. Por seguir estritamente a regra de escopo do `AGENTS.md`, não modifiquei esse arquivo; o helper `_fail_job` no `pipeline_runner.py` garante compatibilidade segura entre `DurableTaskQueue` e `SQLiteTaskQueue`.
- No ambiente Windows com pouco espaço no disco `C:`, o SQLite necessita que variáveis `TMP` e `TEMP` apontem para diretório no disco `L:` (`L:\Fast-Clipper-S1\data\_tmp`) para não disparar `sqlite3.OperationalError: database or disk is full`.
